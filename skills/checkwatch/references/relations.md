# Relations — how the sections pull on each other

The sections are not independent. Most projects that lose their way had a tension between two
sections that nobody named at the start. After the user gives their own view, walk these pairs and
name every tension you find.

## Pairwise questions

| Pair | Question to ask yourself | Tension looks like |
|---|---|---|
| **Problem ↔ Constraints** | Can the final objective be reached inside these limits? | "Nationwide rollout" with a budget for one city. |
| **Problem ↔ Tools** | Does each tool move toward the objective, or toward something else? | A tool chosen for a different goal ("we use X because we always do"). |
| **Problem ↔ Context** | Is the problem real in this field, and is it backed by the referenced works? | A problem nobody in the stated context has; no evidence it exists. |
| **Constraints ↔ Tools** | Does any tool break a constraint (cost, skills, licensing, data rules)? | A paid service under a zero-budget constraint; a language nobody on the team knows. |
| **Context ↔ Constraints** | Are there limits implied by the context that are missing from Constraints? | Healthcare context with no data-protection constraint listed. |
| **Context ↔ Tools** | Are the tools normal for this field, or is there a reason to deviate? | A field-standard tool ignored without a reason; referenced works that used a different method. |
| **Standard ↔ everything** | Can each criterion actually be checked with this context, these tools, under these limits? | A criterion that needs data the constraints forbid collecting. |

## How to present them

1. Ask first: *"How do you see these sections relating to each other?"* Let the user answer in
   their own words — their view of the relations is itself part of the methodology assessment.
2. Then list your view, most serious tension first:
   > **Constraints ↔ Tools** — "Budget is 0" but "Tableau" needs a paid licence.
   > Options: switch to a free tool, raise the budget, or accept the cost. Which one?
3. For each tension, the user resolves it (change a section) or accepts it (record it under
   *Relations* as an accepted risk).
4. Write the resolved and accepted relations into the logbook's *Relations* section. Checkpoints
   re-test accepted risks.

## Common patterns

- **Solution posing as problem** — the Problem names a tool. Ask for the problem behind it.
- **Hidden constraint** — a tool is "mandatory": it is a constraint, record it in both places.
- **Orphan tool** — a tool linked to no section. Ask why it is there.
- **Unanchored objective** — the final objective has no criterion in the Standard that measures it.
- **Referenceless context** — no referenced works; ask whether this is new ground (fine, record it)
  or an unstated source.
